# Taste
- Prefers data-driven content: page/section content lives in typed data files (e.g. `data/solutions.ts` + a `Solution` interface) rather than hardcoded inside pages or components. Confidence: 0.9
- Prefers reusable Vue components over duplication: extend existing components with optional props (e.g. `title`, `background`) instead of creating near-identical copies. Confidence: 0.9
- Rejects generic SEO filler: each page must have specific, differentiated copy that answers concrete questions (what problem it solves, who needs it, what gets built, common features, technology, process, next step). Confidence: 0.8
- Wants comprehensive SEO implementation on content pages: metadata, canonical, OpenGraph, dynamic per-page metadata, structured data (Article + BreadcrumbList JSON-LD schema), internal links, sitemap, and RSS. Confidence: 0.9
- Wants internal linking between related content sections (solutions/services, industries, case studies, blog). Confidence: 0.6
- Develops in numbered phases (PHASE 4, PHASE 5, ...) driven by detailed structured specs; each phase is a self-contained build brief with explicit requirements and acceptance criteria. Confidence: 0.8
- Requires testing all routes after implementation (HTTP status codes, required page sections, 404 handling, static export output). Confidence: 0.8
- Never fabricates client names, statistics, revenue, performance improvements, user counts, or testimonials; when verified metrics are unavailable, uses qualitative outcomes and enforces this structurally in the data model (e.g. outcome `type: 'metric' | 'qualitative'`). Explicitly requires no fake statistics in content. Confidence: 1.0
- Content data models should mirror the backend/CMS schema (e.g. case study fields matching the Laravel `case_studies` migration) so real project data can be inserted through the CMS, with `published`/`featured` flags driving what renders. Wants "CMS-ready architecture" for new content systems. Confidence: 0.9
- Every blog/article page must follow a strict content structure: search intent, a clear upfront answer, detailed explanation with sections, real examples, pros/cons, related services, FAQ, and a CTA. Confidence: 0.9
- Wants lead magnets with gated download architecture: a downloadable asset (e.g. a checklist) unlocked by a capture form (name, email, company, role, main challenge) and wired into the lead pipeline as its own lead type. Confidence: 0.8
- Wants showcase/marketing pages to be visually exceptional — rich cards, hover interactions, badges, gradient placeholders, polished section layouts — rather than plain content lists. Confidence: 0.6
- Wants professional post-submission success experiences: after a lead/form submission, show a confirmation message ("Thanks — your request has been received.") with a numbered what-happens-next sequence and follow-up CTAs — never just a generic "Success" state. Confidence: 0.9
- Wants marketing attribution on lead capture: UTM source/medium/campaign/content, referrer, and landing page captured client-side and persisted (first-touch, e.g. sessionStorage) so a later conversion keeps the original source. Confidence: 0.8
- Requires production-grade form/lead handling on the backend: validation, rate limiting, storage, notification, and tracking are all explicit, non-negotiable requirements for any lead capture system. Confidence: 0.9
- Prefers clean, reusable backend service architecture (service classes + enums + form requests + resources + notifications) over logic packed into controllers; explicitly asks for "clean reusable lead service architecture". Confidence: 0.8
- Wants clean architecture without unnecessary abstractions: "use clean Laravel architecture" but "do not build unnecessary abstractions" — avoid over-engineering and speculative generic layers; keep the build lean. Confidence: 0.7
- Never trust client-side validation alone: wants validation on both frontend and backend, with server-side validation as the authoritative layer (repeated as an explicit non-negotiable requirement for admin CRUD and form APIs). Confidence: 0.8
- For admin/back-office systems: prefers Sanctum token auth (rate-limited login), role-based authorization (roles/permissions middleware), secure sessions, and the admin UI built inside the Nuxt app (a /admin section) consuming the Laravel REST APIs — not a separate admin frontend. Confidence: 0.7
- During audit/release phases, avoids scope creep: fix issues rather than add major new features unless required to resolve a problem ("Do not add major new features unless required to fix an issue"). Confidence: 0.7
- Wants conversion event tracking built into shared components (CTA clicks, form submissions with success/error, outbound booking/email/WhatsApp clicks), ideally provider-agnostic (dataLayer-style) so it plugs into GA/GTM without loading third-party scripts. Confidence: 0.7
- Release-readiness includes accessibility compliance: skip-to-content link, dynamic aria-expanded/aria-controls on toggles and accordions, visible focus rings, reduced-motion support, and AA contrast. Confidence: 0.7
- Requires security hygiene at release: secrets and env files gitignored (including subprojects — backend/.env, vendor, sqlite, logs) and env templates documenting credentials with production-change warnings. Confidence: 0.6
- Requires responsive verification across a full range of viewports (320–1920), fixing overflow, text clipping, navigation, and form issues before release. Confidence: 0.6
- Refuses to declare work complete while critical issues remain open, and reports verification honestly — does not claim checks (e.g. real cross-browser testing, Lighthouse) that the environment couldn't actually run. Confidence: 0.7
- Prefers the established navy + signal-blue brand palette and rejects wholesale color-voice changes that weren't requested (e.g. an amber "engineering-drafting" recolor was explicitly reverted: "previous color combination was good. revert that color."). Color experiments should not replace an approved brand without the user asking for it. Confidence: 1.0
- Wants the homepage hero to be premium, user-friendly, and responsive: a trust-cue eyebrow badge, benefit-led subheadline, full-width CTAs on mobile, reassurance microcopy (e.g. "No obligation. Response within one business day."), and decorative visuals hidden on small screens. Confidence: 0.7
- Wants to review a plan before any execution: for multi-step work (e.g. Docker/VPS deployment) the user explicitly asked "make a plan then show me to review it... then if there is any correction then I will instruct you" — plan first, wait for approval/corrections, then implement. Confidence: 0.9
- Wants concrete, copy-paste-ready server/deployment guidelines: exact VPS commands (Docker install, directory layout), file-by-file setup instructions, deploy workflow, and troubleshooting — not high-level summaries ("give me concrete guideline on my vps server"). Confidence: 0.8
- For multi-project VPS deployment: prefers isolated per-project `docker-compose.yml` files sharing one host-level reverse proxy (Caddy routing by domain/path), each project on its own Docker network, a database in its own container with named volumes, and secrets via gitignored `.env` files. Confidence: 0.6
- Prefers marketing heroes/surfaces to lead with concrete proof of work — real client names and project types drawn from actual case-study data, linked to their case-study pages — over generic decorative illustrations that "could belong to any product"; structures the hero as a decide surface (claim + proof + one dominant action). Confidence: 0.6
- Deletes dead code completely when it becomes unused (removed the now-orphaned ArchitectureVisualization component and redundant nginx/dockerignore files) rather than leaving leftovers in the repo. Confidence: 0.6
